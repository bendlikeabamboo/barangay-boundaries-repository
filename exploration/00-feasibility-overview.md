# Feasibility Study: PSGC-Hierarchical GeoJSON from NAMRIA Shapefiles

> **Status:** Exploration / Pre-implementation
> **Date:** 2026-06-14
> **Goal:** Transform NAMRIA's flat `adm{0-4}.geojson` outputs into PSGC-hierarchy-organized files (e.g. `provinces.geojson`, `hucs.geojson`, `municipalities.geojson`, `component_cities.geojson`, `barangays.geojson`) using the `barangay` package's `search_fuzzy` to classify and enrich each feature.

---

## 1. The Problem

NAMRIA shapefiles use a **5-level administrative hierarchy** (ADM0–ADM4):

| NAMRIA Level | Count | Represents |
|---|---|---|
| ADM0 | 1 (3640 polygons) | Philippines (country) |
| ADM1 | 17 | Regions |
| ADM2 | 88 | Provinces + HUCs + MM districts + SGA |
| ADM3 | 1,642 | Municipalities + Cities (HUC/ICC/CC) + SGA sub-areas |
| ADM4 | 42,048 | Barangays + non-administrative areas |

**The core mismatch:** NAMRIA mixes distinct PSGC entity types into single layers. ADM3 alone contains **all four LGU types** (municipalities, HUCs, ICCs, component cities) with no `city_class` attribute to distinguish them. A consumer who needs "just the municipalities" or "just the HUCs" must post-process.

**What we want instead:**

```
provinces.geojson              ← 82 features
regions.geojson                ← 17 features
municipalities.geojson         ← ~1,493 features
highly_urbanized_cities.geojson← 33 features
independent_component_cities.geojson ← 6 features
component_cities.geojson       ← ~111 features
submunicipalities.geojson      ← 14 features
barangays.geojson              ← ~42,010 features
special_geographic_areas.geojson ← 1 feature
```

Each feature would carry PSGC enrichment: `psgc_id`, `psgc_code`, `psgc_name`, `psgc_type`, `match_confidence`, and resolved hierarchy fields (`region`, `province`, `municipality`, etc.).

---

## 2. The Two Hierarchies Don't Align

This is the fundamental challenge. PSGC and NAMRIA disagree on **parent-child relationships**:

### 2.1 The HUC Nesting Problem

| Entity | PSGC Parent | NAMRIA Parent |
|---|---|---|
| City of Baguio (HUC) | Region CAR (`1400000000`) | Benguet province (`PH01285`) |
| City of Cebu (HUC) | Region VII (`0700000000`) | Cebu province (`PH07222`) |
| City of Naga (HUC) | Region V (`0500000000`) | Camarines Sur (`PH05175`) |

NAMRIA **geographically nests** HUCs inside their surrounding province. PSGC **administratively** places them directly under the region. This means:

- An HUC's `ADM2_PCODE` in NAMRIA = the province it sits in (not the region)
- An HUC's PSGC `parent_psgc_id` = the region code
- A simple PCODE join will **fail** because the NAMRIA ADM3 pcode doesn't match the PSGC city pcode prefix

### 2.2 Metro Manila

NCR has **no PSGC province-level units**. NAMRIA represents it as 4 legislative districts (`PH13001`–`PH13004`) at ADM2. PSGC treats all 17 NCR cities/municipality (Pateros) as direct children of the region.

### 2.3 Special Geographic Areas (SGA)

BARMM has a single SGA entity in PSGC that spans multiple geographically disconnected areas. NAMRIA maps this as a virtual ADM2 province.

### 2.4 Independent Component Cities

ICCs have the same nesting ambiguity as HUCs — PSGC places them under the region, NAMRIA nests them under a province. However, some ICCs in PSGC have parent codes that look like province codes (e.g., Cotabato City parent = `1908700000` which looks like a municipality).

---

## 3. Classification Strategy: How to Determine PSGC Type

The central question is: **given an ADM3 feature with a NAMRIA name and pcodes, what PSGC entity type is it?**

### 3.1 Strategy A: PCODE Prefix Matching (Fast, Deterministic)

The existing pipeline (`enrich.py`) already does exact PCODE matching:

1. Build lookup maps from `bg.municipalities`, `bg.cities`, `bg.hucs`, `bg.iccs`, `bg.component_cities`, `bg.submunicipalities`, `bg.special_geographic_areas`
2. For each ADM3 feature, try matching `ADM3_PCODE` against all lookup maps
3. If a match is found, the entity type is **inherited from the matched DataFrame**

**Coverage:** This works for ~85–90% of ADM3 features where NAMRIA pcodes align with PSGC. The existing `_fallback_search_batch` in `enrich.py` handles the remainder.

### 3.2 Strategy B: HUC Mapping (Already Implemented)

The `huc_adm2_mapping.json` artifact (generated by `generate_huc_mapping.py`) already solves the HUC nesting problem with:
- `namria_adm3_to_psgc`: maps NAMRIA ADM3 pcodes to PSGC pcodes for HUCs/ICCs
- `virtual_provinces`: maps NAMRIA's non-standard ADM2 codes (MM districts, SGA) to PSGC codes
- `huc_cities_under_province`: records which HUCs are nested under which provinces

**This is the foundation we build on.**

### 3.3 Strategy C: `search_fuzzy` Classification (New — The Key Enabler)

The `barangay` package's `search_fuzzy` can classify an entity by name when PCODE matching fails.

**The critical insight** (discovered during benchmarking): `match_hooks` controls which record set is searched:

```python
search_fuzzy("Baguio", level=AdminLevel.HIGHLY_URBANIZED_CITY,
             match_hooks=["highly_urbanized_city"], limit=1)
# → City of Baguio (1430300000), score=100.0
```

| Desired Type | `level` | `match_hooks` | Search Space |
|---|---|---|---|
| Province | `PROVINCE` | `["province"]` | 82 records |
| Municipality | `MUNICIPALITY` | `["province", "municipality"]` or `["municipality"]` | 1,493 records |
| HUC | `HIGHLY_URBANIZED_CITY` | `["highly_urbanized_city"]` | 33 records |
| ICC | `INDEPENDENT_COMPONENT_CITY` | `["independent_component_city"]` | 6 records |
| Component City | `COMPONENT_CITY` | `["component_city"]` | 111 records |
| Submunicipality | `SUBMUNICIPALITY` | `["highly_urbanized_city", "submunicipality"]` | 14 records |
| Barangay | `BARANGAY` | `["barangay"]` (default) or with context | 42,010 records |
| SGA | `SPECIAL_GEOGRAPHIC_AREA` | `["special_geographic_area"]` | 1 record |

**Multi-level hooks work** for `["province", "municipality"]` (the fuzzer_base has a pre-concatenated `rp000m00b` column), but region+city hooks (e.g. `["region", "highly_urbanized_city"]`) return no results because the fuzzer_base only has region+city+barangay concatenations, not region+city.

### 3.4 Classification Algorithm (Proposed)

For each ADM3 feature, run this cascade:

```
1. PCODE exact match against all entity-type lookup maps
   → If hit: classify by the matched DataFrame's type. DONE.

2. HUC mapping lookup (namria_adm3_to_psgc)
   → If hit: look up the PSGC record by psgc_id, classify by type. DONE.

3. Name-based classification via search_fuzzy
   a. Try all city types: search_fuzzy(name, hooks=["highly_urbanized_city"])
      then ["independent_component_city"], then ["component_city"]
   b. Try municipality: search_fuzzy(name, hooks=["province", "municipality"])
   c. Accept the highest-scoring result above threshold (≥85 for city types,
      ≥80 for municipality — cities are rarer and more distinctive)
   → Classify by the matched AdminLevel. DONE.

4. If still unmatched: classify as "unresolved" for manual review
```

**Why try city types before municipality?** Many barangays and municipalities share names with cities. "San Carlos" exists as a component city, a municipality, and multiple barangays. Cities are scarcer (150 total vs 1,493 municipalities), so a high score against a city hook is more trustworthy. The `level` post-filter ensures we don't get barangay false positives.

## 4. Scaling Analysis

### 4.1 Feature Counts by Target Output

| Output File | Est. Features | Source Layer(s) |
|---|---|---|
| regions.geojson | 17 | ADM1 |
| provinces.geojson | 82 | ADM2 (subset) |
| municipalities.geojson | ~1,493 | ADM3 (subset) |
| highly_urbanized_cities.geojson | 33 | ADM3 (subset, re-nested) |
| independent_component_cities.geojson | 6 | ADM3 (subset, re-nested) |
| component_cities.geojson | ~111 | ADM3 (subset) |
| submunicipalities.geojson | 14 | ADM4 (subset) |
| barangays.geojson | ~42,010 | ADM4 |
| special_geographic_areas.geojson | 1 | ADM2/ADM3 (virtual) |

### 4.2 Performance Benchmarks

Benchmarked on this machine (2026-06-14):

| Operation | Time | Notes |
|---|---|---|
| `search_fuzzy` cold start (first call) | ~2.3s | One-time fuzzer_base load |
| `search_fuzzy` warm (subsequent) | ~0.18–0.19s per query | After cache is populated |
| 10 warm queries | ~1.9s total | Linear, no batching |

**At scale for ADM4 (42,010 features):**

The existing `enrich.py` already handles ADM4 in two phases:
1. **PCODE + parent-scoped fuzzy** (fast, ~85% of features): Uses in-memory dictionaries, no `search_fuzzy` calls
2. **`search_fuzzy` fallback** for unmatched (~15%): Runs multi-pass hooks

Estimated time for 42,010 ADM4 features:
- If 15% need fallback: ~6,300 features × ~0.19s = **~20 minutes**
- If 10% need fallback: ~4,200 × 0.19s = **~13 minutes**

**For ADM3 (1,642 features):** If all need classification via `search_fuzzy`: 1,642 × ~0.19s = **~5 minutes**. But PCODE matching should handle ~90%, reducing to ~160 × 0.19s = **~30 seconds**.

### 4.3 Memory

The fuzzer_base parquet is ~42K rows × 17 columns. The `barangay` package loads it into memory. Combined with GeoPandas for 42K polygon features, peak memory usage is estimated at **1–2 GB**. This is feasible on a development machine.

### 4.4 I/O — File Sizes

The existing `adm4.geojson` at tolerance=0.005 is already the largest output (~100–200 MB). Splitting into PSGC-hierarchical files:
- `barangays.geojson` will be similar size (dominant)
- All city/municipality files combined: <50 MB
- No additional I/O burden — we're reorganizing, not creating new data

## 5. Feasibility Verdict

### Can this be done? **Yes, with high confidence.**

| Aspect | Feasibility | Rationale |
|---|---|---|
| ADM0/ADM1 → regions | ✅ Trivial | 1:1 mapping, already implemented |
| ADM2 → provinces | ✅ Trivial | PCODE prefix match, ~82 features |
| ADM3 → municipalities + cities | ✅ Feasible | PCODE match (~90%) + search_fuzzy fallback (~10%) + HUC mapping |
| ADM4 → barangays | ✅ Feasible | Already implemented in `enrich.py`, just needs reorganization |
| ADM4 → submunicipalities | ⚠️ Needs logic | Submunicipalities are nested under HUCs in PSGC; need parent-based extraction |
| SGA extraction | ⚠️ Edge case | Single virtual entity, needs manual mapping |
| MM districts | ⚠️ Edge case | No PSGC equivalent at ADM2; 17 NCR LGUs must be extracted from ADM3 |

### Key Risks

1. **Name ambiguity in `search_fuzzy`:** "San Carlos", "San Jose", "Santa Maria" appear as multiple entity types. Mitigation: always use `level` post-filter + hierarchical context in queries.
2. **Cold-start latency:** ~2.3s for first `search_fuzzy` call per version. Mitigation: warm-up call at pipeline start.
3. **ICCs with province-like parents:** Cotabato City, Dagupan, Naga, Santiago, Ormoc have parent codes that don't cleanly resolve. Mitigation: the HUC mapping already handles these.
4. **Non-administrative areas in ADM4:** Forest lands, timber lands, cemeteries (~20 features) must be filtered out (already handled by `_NON_ADMIN_PATTERNS` in `enrich.py`).
